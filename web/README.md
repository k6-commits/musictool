# musictool 試作（Phase 0）

歌う（またはスマホの録音ファイルを開く）→ 音程を検出 → ノート（C / D / E…）に割り当て → ピアノロールで直す → MIDI に書き出す、までが動く試作です。画面は [デザイン](../docs/design.md) の「PC 02 録音・編集」をもとにしています。

- スマホ・PC のブラウザで開く: https://k6-commits.github.io/musictool/ （HTTPS なのでマイクが使えます。main に入るたびに GitHub Pages へ自動で出ます。下の「スマホで使う」）
- claude.ai で開く: https://claude.ai/artifact/MwgWYbftrod7iuYvyjep5J （非公開。共有はページの Share メニューから）
  - claude.ai 上ではマイクが使えないので、**音声ファイルを開く**か**内蔵サンプル**で試せます。保存は ZIP（中に .mid / .wav）
- 手元で動かすこともできます（下記）

## ローカルで動かす

Node.js 22 以上が必要です。

```bash
cd web
npm install
npm run dev
```

ブラウザで http://localhost:5173 を開きます（PC の Chrome / Edge / Safari / Firefox）。localhost なのでマイクが使えます。

1. ●（または R キー）を押すと 4 拍のカウントのあと録音が始まります。歌うと鍵盤が光り、声の線とノートがその場で描かれます（マイクは録音中だけ開きます。1 テイク 10 分まで）
2. もう一度 ● で停止するとすぐにノートになります（録音中に解析した結果をそのまま使います）
3. 黄色の「!」は自信のない音です。右の「確認」から開き、鍵盤の形の候補から選びます（↑↓ キーでも半音ずつ動かせます）
4. SCALE つまみでキーの音に寄せる強さ、GRID つまみでタイミングをそろえる強さを変えます（元の解析結果は残るので何度でも戻せます）
5. 「書き出す」→ MIDI ＋ 声（.zip）/ MIDI（.mid）/ 声（.wav）。MIDI と WAV はどちらも 1 小節目の頭から始まるので、DAW の 1 小節目に置けばそろいます

フォルダのボタンかドラッグ＆ドロップで、スマホのボイスメモなどの音声ファイル（wav / mp3 / m4a など、6 分まで）も読み込めます。クリックなしで録った音声は、最初の音を 1 小節目の頭にしてテンポを推定します。

| キー | 操作 |
|---|---|
| R | 録音 / 停止 |
| Space | 再生 / 停止 |
| Home | 先頭へ |
| ↑ ↓ | 選んだノートを半音上げる / 下げる |
| ← → | 前 / 次のノートを選ぶ（何も選んでいないときはカーソルの位置から） |
| Delete | 選んだノートを削除 |
| ⌘Z / Ctrl+Z | 元に戻す |
| ⌘E / Ctrl+E | 書き出し |

設定（つまみのアイコン）: 音名の表記（C D E / ドレミ）、中央のド（C3 / C4 / C5）、入力（歌声 / ハミング / 口笛）、遅れ補正（「測る」で自動）、計測値（解析速度・有声率・チューニングのずれ・遅れ・実測した往復の遅れ）。

## スマホで使う

iPhone は Safari、Android は Chrome で https://k6-commits.github.io/musictool/ を開きます。

1. **最初に遅れを測ります。** 設定 →「測る」。イヤホンを外し、音量を上げて、静かなところで押してください。5 秒ほど「チッ」という音が 10 回鳴り、スピーカーからマイクまでの往復の遅れを測って補正に入れます（途中でやめるときは「やめる」）。聞き取れなかったときは補正を変えずに知らせます。結果はこのブラウザに残りますが、サイトのデータを消したときや、Safari を 7 日ほど開かなかったときは消えるので、もう一度測ってください（未測定のまま録音を始めると知らせます）
2. ● で録音します。クリックを聞きながら歌うなら有線イヤホンがおすすめです。測った値はスピーカーと内蔵マイクでのものなので、マイク付きのイヤホンなど別のマイクで録るときは録音の始めに知らせます。ずれていたら補正を手で動かしてください。Bluetooth イヤホンは遅れが大きく、測った値と合わないことがあります
3. 「書き出す」→「共有」で、.mid と .wav を AirDrop・メッセージ・ドライブなどへそのまま送れます。Android の Chrome は .mid を共有できないので、MIDI を含む書き出しでは「共有」を出しません（声の .wav だけなら出ます）。共有できなかったときはダウンロードに切り替えます。PC の DAW では 1 小節目の頭に置きます

## しくみ

```
マイク（自動音量調整・ノイズ除去はオフ）/ 音声ファイル
  → 16 kHz にリサンプル（窓付き sinc）
  → 16 ms ごとに基本周波数と確からしさ: 歌声・ハミングは SwiftF0（小さなニューラルネット。雑音に強い）、
    口笛は YIN（SwiftF0 の上限 2.1 kHz を超えることがあるため）。SwiftF0 の前にテイクの音量をそろえる
    （声の部分の RMS を −20 dBFS に。マイクの感度で結果が変わらないように）。SwiftF0 が 700 Hz 以上で
    ビブラートのない音を 1 オクターブ上と答えたときは、確かな YIN の答えでオクターブを直す（eval/README.md）
  → ノート分割（src/transcribe/segment.ts）
      ・自信の低いフレームと、テイク自身の音量に対して小さすぎるフレームを除外（マイクの感度に左右されない）
      ・オクターブの飛びを近くの中央値に合わせて修正
      ・歌い手全体の音程のずれ（例: 全体に 15 セント高い）を推定して差し引く
      ・約 250 ms の中央値から 0.7 半音以上、5 フレーム（80 ms）続いたら次の音（ビブラートでは切れない）
      ・音の入りのしゃくり（下から最大 ~220 ms）はその音の一部として扱い、音の頭はしゃくりの始まり
      ・同じ高さの言い直しは音量の谷で分ける。息っぽい無音程は短いものだけ許す
      ・音高 = 中央 60% の中央値。半音の境目に近い音・揺れの大きい音・短すぎる音に「!」
      ・ベロシティはテイクの中での音の大きさ（マイクの感度ではなく）
  → キー推定（Krumhansl のプロファイル。4 音未満なら調を決めずクロマチック）、スケールへの吸着とクオンタイズ（元データは変えない。2 つの音が同じ位置に寄っても重ならない）
  → MIDI（SMF タイプ 1・480 PPQ・テンポ / 拍子 / 調号つき）と WAV（16 bit）
```

録音中は遅れのない YIN でその場で解析して、声の線と確定したノートを表示します（直近 20 秒だけを解析し直すので、長く録っても重くなりません）。録音を止めると、歌声・ハミングのテイクは SwiftF0 で解析し直します（1 分のテイクで PC なら 2 秒ほど。その間も録ったばかりの音を表示したまま）。録音の頭合わせは、クリックを鳴らした時刻と AudioWorklet が受け取ったフレーム番号から計算し、出力・入力の遅れを足しています。ブラウザが申告する遅れは端末によって当てにならない（出力の遅れを返さないブラウザもある）ので、「測る」ではスピーカーから 10 ms のチャープ（1〜6 kHz）を間隔をずらして 10 回鳴らし、マイクの録音との相互相関で往復の遅れを測ります（`src/audio/latency.ts`。録れたチャープから順に計算するので、終わったときに待たされません。合成した部屋・雑音・歌声で 1〜2 サンプル以内。無音のマイクは「聞き取れない」と判定します）。申告値との差を補正として残すので、出力先が変わってもブラウザが申告するぶんは追従します。補正は手でも動かせます。ステレオの入力は左右を混ぜて使います。

入力モード（歌声 / ハミング / 口笛）を変えるとテイクを解析し直しますが、手で直した音と削除した音は時間の位置で引き継ぎます。

## テストと計測

```bash
npm test          # 単体テスト（79 件）
npm run typecheck # 型チェック
npm run eval      # 合成音声で精度を測る
npm run e2e       # ビルドして Chromium で通しテスト（72 項目）
npm run eval:fetch && npm run eval:real   # 本物の声と雑音で精度を測る（データ約 230 MB、eval/README.md）
```

`npm run e2e` には Playwright と Chromium が必要です（最初に一度）:

```bash
npm i -D playwright && npx playwright install chromium
```

- `npm run e2e` は Chromium の疑似マイクに合成した歌声を流し、録音 → ノート → MIDI 書き出し → MIDI を読み直して照合、ファイル読み込み・ドロップ、5 分のテイク、ノートの修正と元に戻す、キーボード操作、スマホのスワイプ、ステレオ入力、AudioWorklet が使えないときの代替経路、遅れの自動測定（スピーカーの音を 120 ms 遅れて聞くループバックのマイクで測り、続けて録ったテイクのクリックが拍に合うこと。聞こえないマイク、途中でやめる）、スマホの共有ボタン（iPhone と Android の違い、共有できないときのダウンロード）、claude.ai 上と同じ条件（マイクなし・ZIP 保存）までを確かめます。画面のスクリーンショットは `e2e/out/` に出ます
- `npm run eval` の結果（2026-11-14、合成音声 17 条件・各 17 音）:

| 条件 | 正解 | F1 | 音の頭のずれ |
|---|---|---|---|
| テノール / バス / アルト / ソプラノ | 17/17 | 1.00 | 6〜10 ms |
| 全体に +35 / −40 セントずれ | 17/17 | 1.00 | 8〜9 ms |
| 大きなビブラート（±60 セント） | 17/17 | 1.00 | 8 ms |
| 雑音 −25 dB / −18 dB | 17/17 | 1.00 | 5〜6 ms |
| 深いしゃくり（150 セント / 100 ms、200 セント / 150 ms） | 17/17 | 1.00 | 5〜7 ms |
| 小さな声で切れ目なく（−40 dBFS） | 17/17 | 1.00 | 6 ms |
| 息継ぎなしのレガート（150 BPM）/ 音量の揺れ（±2.5 dB） | 17/17 | 1.00 | 6〜8 ms |
| 速い（150 BPM）/ ハミング / 口笛 | 17/17 | 1.00 | 6〜7 ms |

解析は 16 ms の音に対して SwiftF0 で約 0.5 ms、YIN（口笛）で約 0.25 ms です（16 kHz への変換を含む、PC の 1 スレッド）。5 分の音声ファイルは SwiftF0 で 10 秒ほど。歌声とハミングの切り替えは SwiftF0 の結果を使い回すので、ノート分割をやり直すだけです。

### 本物の声での精度（`npm run eval:real`、詳しくは [eval/README.md](eval/README.md)）

公開データの独唱（vocadito、40 曲）とハミング（HumTrans、120 本）に、実環境の雑音（DEMAND）を混ぜた条件も加えて測っています。数字はノート単位の一致（音の頭 ±50 ms・音高 ±50 セントの F1、%）。

| 条件 | YIN 歌 | SwiftF0 歌 | YIN ハミング | SwiftF0 ハミング |
|---|---|---|---|---|
| 静か | 68.9 | 67.5 | 61.7 | 62.7 |
| 道路の雑音 10 dB | 57.8 | 65.4 | 49.0 | 59.3 |
| カフェテリア 0 dB | 16.8 | 53.0 | 17.7 | 43.6 |

歌の正解は人の採譜で、採譜者 2 人どうしの一致は 74.0 %。静かな録音ではエンジンの差は小さく、取りこぼしの多くはノート分割から来ています。雑音が入ると YIN は声を見落とし、SwiftF0 は保ちます。

## ファイル構成

```
src/
  main.ts              画面の状態と操作
  dsp/                 リサンプル・YIN・FFT・ピッチ追跡（まとめて / その場で）
  dsp/swiftf0/         SwiftF0 の移植（重み・WebAssembly カーネル・推論）
  transcribe/          ノート分割・並べ替え（吸着・クオンタイズ）・テンポ推定・採点
  music/               音名・スケール・キー推定
  audio/               マイク入力・再生（簡易シンセ・メトロノーム）・遅れの測定（latency.ts）・WAV
  midi/smf.ts          MIDI ファイルの書き出し
  ui/                  ピアノロール（canvas）・つまみ
  synth/voice.ts       合成の歌声（サンプルとテスト用）
  app/files.ts         書き出しファイルと ZIP
  body.html, styles.css
scripts/               build（1 ファイルの HTML に）・dev サーバー・TypeScript の実行（run-ts.mjs：eval など）・評価データの取得・SwiftF0 の書き出し / カーネルのビルド
tests/                 単体テスト（vitest）
e2e/                   Chromium の通しテスト
eval/                  合成音声での精度計測（eval.ts）と本物の声での評価（real.ts、real/）
wasm/                  SwiftF0 の畳み込みカーネル（AssemblyScript）
```

`npm run build` で `dist/index.html`（そのまま開ける 1 ファイル）と `dist/artifact.html`（claude.ai 用）ができます。GitHub Pages には `.github/workflows/pages.yml` が、型チェックと単体テストのあとに `dist/index.html` を出します（リポジトリの Settings → Pages → Source を「GitHub Actions」にしておく）。

## 使っているもの

- SwiftF0（Lars Nieradzik、[swift-f0](https://github.com/lars76/swift-f0) 0.3.0、MIT ライセンス）: モデルの重みを `src/dsp/swiftf0/weights.ts` に書き出して使っています。著作権表示とライセンス文はそのファイルの先頭にあり、ビルドした HTML にも残ります
- 評価データ（vocadito・HumTrans・DEMAND）はリポジトリに含めず、評価のときに取得します（ライセンスは eval/README.md）
