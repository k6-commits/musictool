# 実際の声での評価

合成音声の評価（`npm run eval`）に加えて、公開されている本物の歌声・ハミングと、実際に収録された雑音で精度を測ります。音程検出エンジン（YIN と SwiftF0）ごとに同じノート分割を通して、人が付けた正解と比べます。

## データ

データはリポジトリに入れていません。`npm run eval:fetch` で `eval/data/`（git 管理外）に約 230 MB を取得します。

| データ | 中身 | ライセンス | 使い方 |
|---|---|---|---|
| [vocadito](https://zenodo.org/records/5578807)（Bittner ほか 2021） | 独唱 40 曲・13.6 分（7 言語）。F0 と、2 人の採譜者によるノート | CC BY 4.0 | 採譜者 1 を正解に、採譜者 2 との一致を「人どうしの一致」として併記 |
| [HumTrans](https://huggingface.co/datasets/dadinghh2/HumTrans)（Liu ほか 2023） | ハミングと、その旋律の MIDI | CC BY-NC 4.0（非商用） | テスト分割から 10 人 × 12 本 = 120 本・28 分。18 GB のアーカイブから必要な分だけを範囲指定で取得 |
| [DEMAND](https://zenodo.org/records/1227121)（Thiemann ほか 2013） | 実環境の雑音 | CC BY 4.0 | カフェテリア（PCAFETER）・道路（STRAFFIC）・リビング（DLIVING）の 1 チャンネルを、SN 比 10 dB / 0 dB で声に混ぜる |

HumTrans の MIDI は、録音そのものの採譜ではなく「歌い手が聴いて追った旋律」です。録音は MIDI より遅れ（多くは 0.1〜0.4 秒、人によっては 1.5 秒近く）、低い声の人の多くは 1 オクターブ下（1 本は 2 オクターブ下）で歌っています。そこで録音ごとに一度だけ、ずれ（0〜2 秒）とオクターブ（±2 まで）の組み合わせを、静かな録音での YIN と SwiftF0 のノートの一致数の合計が最大になるように合わせ、すべてのエンジン・雑音条件に同じ合わせ方を使います（どちらのエンジンにも寄らないように）。タイミングの数字は粗めの目安として見てください。

雑音を混ぜた音声は 16 kHz の WAV として一度だけ作り、どのエンジンも同じ音を読みます。SN 比の「声の大きさ」は、32 ms ごとのフレームのうち大きい方の半分の RMS です。

## 実行

```bash
npm run eval:fetch
npm run eval:real -- --conditions clean,living10,street10,cafeteria10,street0,cafeteria0
```

- `--engine yin,swiftf0`（既定。アプリと同じ解析）。`swiftf0-plain` は後述のオクターブ確認なしの SwiftF0、`swiftf0-ref` は参照実装の出力（`eval/real/swiftf0_frames.py` で作ったもの。録音そのままの音量で）
- `--items` で曲ごとの結果、`--json <file>` で詳細（既定は `e2e/out/eval-real.json`）

## 指標

- **COnP**：音の頭が ±50 ms 以内かつ音高が ±50 セント以内で一致したノートの F1（MIREX のノート採譜、mir_eval と同じ照合）。**COnPOff** は音の終わりも一致（音の長さの 20 % か 50 ms の大きい方）、**COn** は音の頭だけ
- **octave**：音の頭は見つかったのに、音高が 1〜2 オクターブずれていたノートの割合
- **seq**：アプリが書き出す音名（チューニングのずれを除いて丸めた番号）を、正解の音名と順番どおりに比べた一致（最長共通部分列の F1、タイミングは見ない。HumTrans のみ）
- **RPA / RCA**：正解で声があるフレームのうち、音高が ±50 セント以内のもの（RCA はオクターブ違いも正解とする）。**VR / VFA**：声のあり・なしの判定の再現率と誤検出率（vocadito の F0 に対して）
- 曲ごとの値の平均。ノートの照合は mir_eval 0.8.2 で検算し、80 組（40 曲 × 2 エンジン）すべてで同じ値（時間差の丸めも mir_eval と同じく偶数丸め）

|---|---|---|
| YIN | 0.25 ms | — |

### 読み方

- 静かな録音では 2 つのエンジンはほぼ同じです。どちらも人どうしの一致（74 %）の 9 割ほどで、取りこぼしの多くはエンジンではなくノート分割（1 つの音を 2 つに割る・2 つの音をつなげる、0.1 秒未満の装飾音＝正解の 22 %）から来ています
- 雑音が入ると差がはっきりします。YIN は声を「声なし」と判定して音を落とし（0 dB で VR 20 % 前後）、SwiftF0 は 0 dB でも音程の 85〜93 % を正しく取ります。スマホを実際の部屋や屋外で使うことを考えて、歌声とハミングは SwiftF0 で解析することにしました
- SwiftF0 の確からしさは入力の音量に左右されます（ピークが −40 dBFS を下回ると急に声を見落とし、−52 dBFS ではノートの一致が 66 % → 25 %）。アプリは自動音量調整なしで録るので、解析の前にテイクの声の部分の RMS を −20 dBFS（評価データの中ほど）にそろえます。これでピーク −12〜−52 dBFS のどこでも同じ結果になります（評価データはすべてピーク −20〜0 dBFS なので、上の表には影響しません）
- SwiftF0 は、ビブラートのない真っ直ぐな音（A4〜D#5 あたり）に少しでも雑音が乗ると、1 オクターブ上と答え続けることがあります（合成音声のソプラノで見つかり、子どもの声などでも起こりえます）。そこで SwiftF0 が 700 Hz 以上と答えたフレームだけ、同じ 32 ms を YIN（範囲 300〜2100 Hz）で調べ、YIN が確か（非周期性 0.1 未満）にちょうど半分と答えたら YIN のオクターブを使います。上の実データでは 1 フレームも変わらず（`swiftf0-plain` と同じ）、時間は 1〜2 % 増えるだけです。700 Hz 未満を調べないのは、低い声では YIN 自身の 1 オクターブ下への誤りが多く、確認がかえって正しい音を落とすためです（最初の版で実際に起きていました）。SwiftF0 自身の出力だけで直す方法（1 オクターブ下の候補が強ければ下を採る）も試しましたが、実データで逆向きの誤りが増えたので採っていません
- 口笛は SwiftF0 の範囲（2.1 kHz まで）を超えることがあるので YIN のまま、録音中の画面表示も遅れのない YIN です

## SwiftF0 の移植

- 重みは swift-f0 0.3.0（PyPI、MIT ライセンス）の ONNX モデルから `scripts/export-swiftf0.py` で書き出しています（`src/dsp/swiftf0/weights.ts`）。STFT・フィルタバンク・畳み込み・音高の取り出しは TypeScript で書き直し、畳み込みだけを WebAssembly SIMD のカーネル（`wasm/swiftf0-kernel.ts`、AssemblyScript。`npm run build:wasm` で再生成）で動かしています。SIMD が使えない環境では同じ計算を TypeScript で行います
- 参照実装（onnxruntime）との差: 雑音入りの 16 kHz 録音 80 本・86,701 フレームで、音高は最大 0.0002 セント、確からしさは最大 2.5×10⁻⁶、声のあり・なしの判定が変わったフレームはなし（`npm run eval:check-swiftf0`。参照の出力は丸めずに保存）
- 長い録音もメモリを食わないよう、少しずつ（128 フレームずつ、前後 7 フレームの文脈つき）計算します。結果は全体を一度に計算したときとビット単位で同じです。1 回の計算は PC で 0.1 秒ほどで、その間に画面が止まります（Worker に移すのが次の課題）
- STFT は 2 フレームを 1 回の複素 FFT にまとめて計算します

## 限界

- どのデータも大人の声で、スタジオに近い録音です。子どもの声、スマホのマイク、本物の部屋の響きは含みません。曲数も多くありません
- 口笛の実データはありません
- PESTO（LGPL-3.0）と Basic Pitch とはまだ比べていません
